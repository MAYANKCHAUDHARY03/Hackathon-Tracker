## Phase 46 — Universal Innovation Ontology 🔴
**Why:** Before adding more AI, the platform needs one canonical vocabulary. Every future module (agents, copilots, analytics, federation) should consume this ontology instead of inventing its own representation — this is what lets a new program type reuse core entities without duplicate models.

**Scope:**
- Define canonical entity types: Person, Organization, Community, Program, Hackathon, Challenge, Problem, Idea, Team, Project, Technology, Skill, Mentor, Judge, Sponsor, Research, Dataset, Startup, Product, Pilot, Opportunity, Achievement, Impact.
- Give every entity a common base shape: `ID, Type, Owner, Source, Verification, Visibility, Created, Updated, Relationships`.
- Build the relationship/graph layer connecting entities.
- Migrate at least one existing module to read/write through the ontology instead of its local schema, as proof of the pattern.

**Definition of done:** A new entity type or program type can be added by reusing existing base entities — no duplicate models required.

## Phase 47 — Universal Event & Activity Stream 🔴
**Why:** Right now, Task/Notification/Analytics/AI/Integration/Audit systems would each track activity independently. A single canonical event stream lets Analytics, AI, and Automation all subscribe to one source of truth instead of drifting out of sync.

**Scope:**
- Define the event envelope: immutable event ID, timestamp, actor, organization, entity, event type, source, correlation ID, metadata. No sensitive credentials in events, ever.
- Implement event types: `project_created, task_completed, challenge_created, team_joined, submission_created, evaluation_completed, award_verified, project_deployed`, plus any others needed by existing modules.
- Wire existing systems (tasks, notifications, analytics) to publish into this stream.
- Build a minimal internal event viewer/log for debugging.

**Definition of done:** Every meaningful platform action produces one immutable, correctly-shaped event, and at least one downstream consumer (e.g. notifications) reads from the stream rather than being called directly.

## Phase 48 — AI Agent Framework 🔴
**Why:** Multiple narrow, permissioned agents are safer than one unrestricted agent. Each agent should only be able to do what its role requires.

**Scope:**
- Build the agent framework/runtime with a registry for: Research Agent, Project Agent, Submission Agent, Mentor Agent, Organizer Agent, Analytics Agent, Documentation Agent.
- Each agent gets an explicit allow-list of tools (e.g. Submission Agent: read project, validate submission, generate checklist, prepare submission — explicitly **not** delete project, change permissions, modify organization, or submit without confirmation).
- Every tool invocation must be permission-checked, logged, traceable, and reversible where possible — build this as shared middleware all agents pass through, not per-agent logic.
- No agent ships with a "high risk" or "critical" action wired up yet — those stay blocked until Phase 49 exists.

**Definition of done:** Agents can be invoked, their tool calls are fully logged and permission-scoped, and no agent can perform an action outside its declared tool list.

## Phase 49 — Human Approval Framework 🔴
**Why:** This is the safety backbone of the entire autonomous layer. Without it, later agents could become uncontrolled automation.

**Scope:**
- Build risk classification: `Low Risk → Automatic`, `Medium Risk → User Approval`, `High Risk → Admin Approval`, `Critical → Blocked/Manual Only`.
- Classify known action types: Low (summarize project, suggest task, generate documentation), Medium (create tasks, modify project metadata, schedule meetings), High (publish project, external communication, external submission), Critical (permission changes, destructive operations, financial operations).
- Build the approval queue/UI: pending approvals show affected entities, exact action, reason, and expected impact.
- Retrofit Phase 48's agent framework so every agent tool call routes through this classifier — no agent may bypass the approval engine, under any circumstance.

**Definition of done:** A medium-or-higher-risk action from any agent cannot execute without passing through this engine, and this is enforced at the framework level, not per-agent.

## Phase 50 — Agent Memory & Context 🔴
**Why:** Agents need context to be useful, but memory must be scoped and revocable — one organization must never be able to retrieve another's memory.

**Scope:**
- Implement three memory layers: Conversation Memory, Task Memory, Organization Knowledge.
- For each agent, define what it's allowed to hold in memory (e.g. Project Agent: current project, tasks, hackathon, team, previous decisions, approved documents).
- Implement scoped memory, expiration, deletion, and provenance tracking.
- Enforce hard organization-boundary isolation on all memory reads.

**Definition of done:** Memory is provably scoped per organization/agent, expires and can be deleted on request, and every memory item is traceable to its source.

## Phase 51 — Autonomous Project Operations 🔴
**Why:** The first real user-facing copilot — proves out the ontology, event stream, agent framework, approval engine, and memory layers together.

**Scope:**

- With approval, allow it to: create tasks, assign tasks, schedule reminders, generate checklists, generate documentation.

**Definition of done:** A real project can be monitored end-to-end by the copilot, with all mutating actions gated by approval and fully logged.
